# 实际复盘

## 本次遇到的工程问题

**模型声明不能决定任务成功。** 将完成条件放在 Runtime；模型只能请求 finish。估时与品牌检查必须属于当前内容指纹，且所有必要字段齐全。通过对抗性预设动作验证，缺证据或缺检查时的 finish 被拒绝。

**验证结果容易过期。** 仅绑定“第几个脚本版本”不够，因为目标时长、素材和规则也影响结果。最终指纹涵盖这些依赖；显式改稿清空检查，完成时再次计算指纹。额外检查了素材本体已变化而检索副本仍旧的情形。

**工具错误后不能沿用先前 pass。** 代码审阅发现，只清空当前出错检查无法覆盖“通过后再检索失败”等路径。已统一在业务工具错误时清空两种当前结果，并添加边界测试。这是 AI 审阅修正，不虚构为候选人人工调试经历或测试先失败。

**程序无法全面判断自然语言事实。** 未使用宽松的“附上引用就通过”策略，而要求原文和批准文案覆盖所有可见文本。这个选择可解释、便于审计，但会误拒合理改写，减弱创作灵活性，需要在未来加入有证据和独立评估的语义核验。

**完成状态不能证明发生动态修订。** 运行脚本会另外核验先前真实超时、随后稿件变化和重新估时。Mock 修订严格标记预设；真实模型未触发修订时不写“修订成功”。

## 实际结果

已完成原生循环、真实请求 Adapter、三个确定性工具、版本与异常处理、结构化输出、自动 Trace、离线场景和文档。实际工具在 Mock 超时场景中估出43.43秒首稿、7.64秒修订稿，目标12秒；没有硬编码总秒数。无据效果声明被阻止完成，工具故障和上限有真实记录。

初始开发首轮测试全部通过，后续代码审阅补了边界与测试；原始记录保留于 `examples/`。用户最初要求先完成离线部分，后续提供 API 后执行真实验证，当时116项 pytest 通过。之后严格验收新增7条对抗回归实际失败，揭示旧测试覆盖不足；修复后当前129项通过，详见严格审计报告。

live 阶段实际保存了10次运行、61条模型响应，覆盖8类场景。除无素材查询改写、注入工具失败后的重试，还观察到4秒目标下7.64→2.35秒的改稿，以及首次引用规则失败后的重新修改与检查。原12秒 overtime 采样首稿10.41秒，没有触发修订；原批次失败的行为断言保留，补充输入独立覆盖超时闭环。这说明“任务完成”和“测试触发指定分支”必须分别报告。

## 可从实现中学到的要点

1. 模型负责下一动作和创作，程序负责可计算的业务不变量；两者都需要可审计证据。
2. 检查必须绑定全部依赖，保留旧历史不等于可以复用旧通过结论。
3. 负向案例明确失败或请求补充，是可靠性验收的一部分。
4. Mock 对工程逻辑有用，但不能证明真实模型会观察反馈并重新规划。

以上为 AI 对实现的技术总结，候选人的个人学习收获需本人确认和改写。
